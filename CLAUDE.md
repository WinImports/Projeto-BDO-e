# BDO-e & Inspeção Técnica

App desktop (Electron) para relatórios de campo de inspeção de poços, manutenção de cabeça de poço/válvulas, leitura de pressões e intervenção de superfície sem sonda. Offline-first com envio ao Supabase.

## Executar e testar

- `npm start` → `electron .` (carrega `./index.html` via `file://`; **não há servidor web, bundler, React ou TypeScript**).
- **PWA / GitHub Pages**: a MESMA `./index.html` roda no navegador/celular (caminhos sempre relativos `./`). `src/core/platform.js` escolhe Electron (`window.desktop`) ou web (base de poços em localStorage/fetch, PDF via janela de impressão com CSS por CSSOM). **Antes de publicar rode `npm run pwa`**: atualiza VERSION e a lista offline do `sw.js` e roda o `npm test` (`npm run pwa:sw` só atualiza). O hook `.githooks/pre-push` (ativado por `npm install` via `prepare` → `core.hooksPath`) **bloqueia o push** se o `sw.js` estiver desatualizado.
- **Celular**: alvos de toque ≥ 44 px e inputs de 16 px (evita zoom do iOS) em `@media (pointer: coarse), (max-width: 640px)`; datas/horas sempre `date`/`time`/`datetime-local`. Elementos `position:absolute` dentro de áreas roláveis precisam de ancestral `position: relative` (senão vazam e criam rolagem lateral — ver `.table-wrap`). Teste: `tests/mobile.spec.js` (janela 390 px).
- **Cloudflare Pages** (site oficial `https://bdo.winappdigital.com.br`, deploy a cada push na `main`): build command `npm run build`, output directory `dist`. O build (`scripts/build-web.js`) só copia os arquivos publicados (nunca `src/data/`), grava `dist/src/env.js` com `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `NEXT_PUBLIC_APP_URL` (recusa chave service_role e URL fora de `*.supabase.co`), soma o hash das variáveis à VERSION do `dist/sw.js` e escreve `_headers` (sw.js/index sem cache). No repositório `src/env.js` fica vazio. **Não é Next.js**: os nomes `NEXT_PUBLIC_*` são só a convenção das variáveis. `CF_PAGES=1` faz o `postinstall` pular o download do Electron. Prioridade do Supabase em `supabaseConfig()`: aparelho > env do desktop > publicação (`origem: 'publicacao'`) > constantes. `appUrl()` (config.js) = `NEXT_PUBLIC_APP_URL` ou a origem da página — use para qualquer redirect do Supabase Auth, nunca localhost.
- **Instalador Windows**: `npm run electron:build` (electron-builder, NSIS, config em `build` do package.json) → `release/BDO-e-Setup-<versão>.exe` (`release/` no .gitignore; `dist/` é do site). O pacote leva só main/preload/electron/index/manifest/icons/src — **inclui** `src/data/pocos-ba.json` (base embutida de poços; só existe na máquina de build, nunca no Git nem no site) e deixa de fora tests, _legado, licencas e node_modules. Editor = `author` (WIN IMPORTS). Usa o Electron já baixado (`electronDist`). Sem certificado: o .exe sai sem assinatura (SmartScreen avisa).
- `npm test` → Playwright abrindo o Electron real (`tests/`). Dados de teste ficam isolados via `BDOE_USER_DATA`.
- `npm install` roda `postinstall` (`scripts/postinstall.js`) que baixa o binário do Electron (o npm desta máquina bloqueia scripts de pacotes).
- Se `npm start` falhar com `reading 'whenReady'`: a variável `ELECTRON_RUN_AS_NODE` está definida (o VS Code injeta). Remova-a antes.

## Arquitetura

```
main.js          processo principal: janela, permissões (só câmera e GPS), IPC pdf:save (printToPDF)
electron/        IPC e parser da base de poços (CSV/KML)
preload.js       contextBridge → window.desktop (savePdf). contextIsolation + sandbox ligados
index.html       página única (Electron + PWA). CSP restrita: scripts só locais; connect-src *.supabase.co; frame-src openstreetmap.org
manifest.json, sw.js, icons/, .nojekyll   PWA (sw.js gerado por scripts/gerar-pwa.js)
src/vendor/      supabase.js (UMD copiado de node_modules: `npm run vendor`)
src/shared/      pocos-parser.js — UMD usado pelo Electron, navegador, script e testes
src/app.js       orquestração: base/abas, layout do formulário, índice de seções, ações, Ctrl+S
src/config.js    credenciais do Supabase (supabaseConfig(): Configurações › Servidor > env BDOE_SUPABASE_URL/_ANON_KEY no desktop > constantes) e parâmetros de sync (vazio = "Somente local")
src/core/        db (IndexedDB), drafts, outbox, sync, supabase, settings, ids, prefs, auth (login), heranca (BDO → relatórios), pull (histórico da equipe)
src/modules/     definições DECLARATIVAS dos formulários (visita-tecnica, bdo, handover, common)
src/ui/          form (renderizador), preview, cabecalho, report-pdf, pdf-doc (jsPDF), bdo-pdf (BDO-e em 1 página), docx-doc (Word), outbox-view, settings-view, login-view, camera, icons, toast
supabase/schema.sql  tabelas, RPCs e Storage (rodar no SQL Editor do Supabase); migrações novas em supabase/migrations/
licencas/        Painel de Licenças Multi-App (index.html + app.js), rota /licencas/: fala SÓ com o Supabase central
                 winappos-licensing (apps, clients, licenses, license_devices, license_logs; RPCs conferidas no servidor:
                 create_license(p_app_id = UUID de public.apps, p_client_id, p_max_devices, p_duration_days),
                 renew_license(p_license_id, p_additional_days), set_license_status(p_license_id, p_status) — objeto RPC
                 do app.js; o mock de tests/licencas.spec.js recusa parâmetros diferentes). Login obrigatório (sessão em
                 `winappos.licencas.auth`), Tailwind v4 browser + Font Awesome por CDN com SRI, supabase do src/vendor.
                 Fora do PWA: o sw.js ignora /licencas/; o build copia a pasta e manda noindex/no-frame. Teste: tests/licencas.spec.js
_legado/         versão antiga — não editar
```

Supabase JS é carregado do **build UMD local** (`src/vendor/supabase.js`, cópia de node_modules) e usado via `window.supabase` em `src/core/supabase.js`. Não importar de CDN. O cliente guarda a sessão do Supabase Auth no localStorage (`bdoe.supabase.auth`, `persistSession` + `autoRefreshToken`): RPC e Storage vão com o token do técnico logado (o servidor grava `user_id`/`user_email`); sem sessão, pela chave anon. Credenciais trocadas em Configurações › Servidor chamam `resetClient()`. Testes simulam o Supabase trocando `window.supabase.createClient` (`tests/supabase.spec.js`).

**Publicação**: repositório público `WinImports/Projeto-BDO-e` com GitHub Pages. A base REAL de poços (`src/data/pocos-ba.json`, CSV/KML) **nunca vai para o Git** (.gitignore) — dados operacionais; no celular a base é importada em Configurações.

## Regras de negócio

- Menu com exatamente 3 relatórios, nesta ordem (`src/modules/index.js`): **BDO-e** (`bdo`), **Relatório de Visita Técnica** (`visita_tecnica`), **Relatório de Execução** (`handover`). Não existe mais seleção de base BA/SE; rascunhos são um por relatório (chave = id do módulo; chaves antigas `BA:x`/`SE:x` são migradas em `core/drafts.js`). A coluna `base` no banco ficou só como legado (nula).
- **Licença** (`core/licenca.js` + `ui/licenca-view.js`, antes do login): projeto Supabase central winappos-licensing (URL/chave publishable próprias em `LICENCA`, app `bdo-e`), só a RPC pública `validate_license(p_app_code, p_license_key, p_device_id = getDeviceId(), p_device_name)` → `{ valid, reason, expires_at, max_devices }` via `fetch`. 1ª abertura: tela `#licenca-form` (ativação precisa de internet); chave e estado em `localStorage` `bdoe.licenca`. Toda abertura valida: com validação ok há < 7 dias abre na hora e valida em segundo plano; senão espera o servidor. `valid=false` bloqueia com o `reason` e zera `ultimaValidacao` (ficar offline não escapa). Sem rede/HTTP ≠ 200: tolera até 7 dias da última validação ok (`avaliarSemRede`), nunca após `expires_at` nem com relógio voltado (`ultimoUso`). Revalida no evento `online` e a cada 6 h. Desligada só no Electron NÃO empacotado com `BDOE_LICENCA=off` (helpers.js liga por padrão; `launchApp({ licenca: true })` testa) e no navegador em localhost. Teste: `tests/licenca.spec.js`.
- **Login por e-mail OU matrícula** (`login()` em `core/auth.js`): sem "@" é matrícula → `login_matricula` no banco (confere a senha, devolve o e-mail só com a senha certa; "bloqueado" após 5 falhas) → `signInWithPassword` com o e-mail. Sem internet: matrícula de quem já entrou neste aparelho (`bdoe.auth.users[email].matricula`, comparada por `normMatricula` = `_norm_matricula`). Mensagens genéricas ("Matrícula ou senha incorretos."). Campo `#login-email` = "E-mail ou matrícula". **Troca de senha obrigatória**: conta criada pelo gestor tem `user_metadata.must_change_password` → sessão com `trocarSenha: true` → `showTrocaSenha()` (`#troca-senha-form`, mín. `SENHA_MIN` = 8, confirmação) cobre o app até `trocarSenha()` gravar (`auth.updateUser({ password, data: { must_change_password: false } })`); precisa de internet.
- **Papéis e Gestão de Equipe** (`core/contratos.js` + `ui/equipe-view.js`): `atualizarContratos` usa `my_access()` (contratos + papel; sem a migração 001 cai no `my_contracts`) e guarda `vinculos` em `bdoe.contratos`; roda no `syncNow` ANTES de enviar a fila. `souGestor()` → aba `equipe` (EQUIPE_TAB) em `renderTabs`; `isTabAvailable('equipe')` é falso para técnico (nem a aba salva abre). Tela: cota "Técnicos cadastrados: X de Y liberados" (`[data-cota-texto]`, barra), cadastro (Nome Completo, Matrícula Funcional, E-mail, Contrato, Senha Inicial + "Gerar") pela Edge Function `create-technician` (`functions.invoke`; erro mostra `corpo.erro`), botão `#eq-cadastrar` desabilitado com a cota cheia + `AVISO_COTA`, lista com Ativar/Desativar só para técnicos (`team_set_active`). Precisa de internet.
- **Histórico sem limite** (`core/busca.js` + seção `[data-history-server]` no `outbox-view.js`): com servidor + internet + conta, "Buscar no servidor" chama `search_team_reports` (texto e filtro de tipo do Histórico, 50 por página, "Carregar mais" com `p_before`); mostra só o que NÃO está no aparelho (status `server`, "No servidor"); fotos baixadas só ao abrir a prévia. O aparelho continua guardando 30 dias (pull) para uso offline.
- **Assistente Técnico de Flanges — busca cruzada, em qualquer ordem** (Visita Técnica, blocos `flange_sup` / `flange_inf`): tabela em `src/shared/flangeTable.js` (NÃO em src/data/, que não é publicado; linhas com `// CONFERIR` = valores a validar com a fonte, gravados como recebidos), lógica em `src/core/flange.js`. Os 8 campos (`flangeCampo`: modelo, pressao, parafusos=furos, anel, diametro, comprimento, chave, torque) filtram juntos (`analisar`): o técnico preenche qualquer um, em qualquer ordem; medidas em pol ou mm ("7/8\"", "22,23", "1-7/16\"", "36 mm"), torque em Nm ou lbf·ft, pressão "5M" ou "5.000 psi"; "3/5M" vale para 3M e 5M; "2 1/16\" DL" é o flange 2 1/16". **Só conta como filtro o que o técnico preencheu** — o que o app preencheu fica em `data._flange_sug` e não filtra (senão travaria ao trocar um campo); valor que não existe na tabela vira anotação (`ignorados`) e não filtra. Cada caixa oferece só o que combina com os OUTROS campos (`opcoesDe`: datalist nos textos/números; no select de Flange/Pressão o resto vai num optgroup "Não combinam com o já preenchido"). `aplicarSugestao` completa o que é comum a todos os flanges que restam (tudo, quando sobra um); o que o técnico preencheu fica. Card de Apoio (`type: 'flangeCard'`, `[data-flange-card]`, `data-estado` incompleto|nenhum|multiplo|unico): "Cruzando: …", até 8 opções (`flange-opcao` → `escolherLinha`), conflito com "Limpar X → N opções" (`flange-limpar` → `limparCampo`), chave, torque e `NOTA_TORQUE`; pressão vazia num flange 3/5M é pedida no card. As caixas são atualizadas NO LUGAR (`atualizarCampoFlange`) e o card só é redesenhado se mudou: o técnico não perde o foco nem o clique. O antigo `<p>_tamanho` é `formHidden` (sai no PDF/Word de relatório antigo). Relatórios: `reportAlways` (modelo, pressão, anel, chave, torque) saem sempre que a seção tiver dado ("—" quando vazios) e `reportNote` vai junto do torque — via `dadosParaRelatorio()` (form.js) na prévia/PDF HTML, no jsPDF e no Word. Testes: `tests/flange.spec.js` (a lógica é testada direto no Node).
- **Relatório em JSON** (`core/relatorio-json.js`, formato `bdo-e/relatorio` v1: `{ formato, versao, exportadoEm, relatorio: { uniqueId, module, createdAt, data, fotos: [{ field, fase, legenda, category, name, dataUrl }] } }`; também lê lista `[...]`/`{ relatorios }` e a linha do banco `{ module, payload, photos }` — foto sem `dataUrl` é ignorada e avisada). **Exportar JSON** na prévia (`[data-json]`; desktop "Salvar como" com filtro .json no `file:save`; navegador painel "JSON pronto"). **Upload de Relatório (JSON)** só na aba Execução (`#btn-import-json` / `[data-import-json]`, `ui/importar-json.js`): resumo, Contrato (lista da conta; variação de escrita → nome da lista), Visualizar, **PDF (paisagem)**, "Só salvar no aparelho" (`saveLocalOnly`) ou "Importar e enviar" (`enqueue` + sync). Salvo, vira o **ANTES** da Execução aberta (`usarComoAntes` no app.js: preenche o poço se vazio; poço diferente não mexe), fixado em `data._antes_fixo` (a consolidação não troca pela última Visita). uniqueId do arquivo é mantido (reimportar não duplica).
- **TODOS os relatórios em paisagem (A4 deitado)**, PDF e Word: jsPDF geral (`new Doc(…, true)`; medidas por documento `doc.W`/`doc.H`/`doc.CW`), BDO-e (`bdo-pdf.js`, `A4 = { w: 297, h: 210 }`), PDF HTML do desktop e "Imprimir" do navegador (`@page { size: A4 landscape }` + `printToPDF({ landscape: true })` no main.js) e Word (`PAGE_W` 16838 × `PAGE_H` 11906, `w:orient="landscape"`; tabelas e fotos derivam da largura). Não há mais botão "PDF (paisagem)".
- **Envio recusado** (`motivoNaoConfirmado` em `core/sync.js`): contrato fora da conta → "O servidor não aceitou este relatório: o contrato "X" não está vinculado à sua conta…"; sem login no servidor (RLS/permissão) → "Entre com a sua conta do servidor para enviar…". O relatório fica na fila.
- **Login** (`core/auth.js` + `ui/login-view.js`): primeira tela sem sessão (`#login-form`, antes de montar as abas). E-mail + senha: com Supabase configurado e internet → `signInWithPassword` no cliente compartilhado (sessão do Supabase salva) e guarda hash PBKDF2 da senha para o login offline; usuário local que configurou o servidor depois vê "Sair e entrar de novo" em Conta para vincular; sem internet/servidor → confere o hash local ou cria o usuário local. Sessão em localStorage (`bdoe.auth.session`); nome no topo (`#user-chip`); "Sair / Logout" em Configurações › Conta (apaga só a sessão e recarrega). Testes: `launchApp()` entra sozinho com usuário local (`login: false` para parar na tela), `tests/fluxo-bdo-relatorios.spec.js`.
- **Poço só no BDO-e**: busca na base, GPS e rotas existem só no BDO-e. Visita e Execução usam `pocoHerdado()` (texto simples) e `module.herdaDoBdo` (`herancaBdo()`): ao abrir, `core/heranca.js` copia do BDO-e ativo (rascunho com poço; senão o último BDO finalizado) Poço, Locação/Campo (← cidade_uf), Data, Cliente, Contrato e coordenadas. Novo relatório recebe tudo; rascunho só nos campos vazios ou ainda iguais ao último valor herdado (`data._bdo`). Aviso `[data-heranca]` no topo. As coordenadas ficam na seção `legacy` (fora do formulário) e **não** saem no relatório.
- **Objetivo protegido**: `defaultValue` (texto padrão) + `lockEdit: 'Editar Objetivo'` → textarea `readonly` até o botão `toggle-lock` ("Concluir edição" trava de novo).
- **Busca no Histórico**: `[data-history-search]` filtra ao digitar (sem acento, todos os termos) por tipo, poço, data (dd/mm/aaaa), status, cliente, ID; só `renderResults()` é refeito (o campo não perde o foco).
- **Base de poços/locações**: importada pelo usuário em Configurações (arrastar ou escolher `.csv`/`.kml`). O parser (`src/shared/pocos-parser.js`) roda no processo principal no desktop e no próprio navegador no PWA e grava `userData/pocos-base.json` de forma atômica; IPC em `electron/pocos.js` (`pocos:list|status|import|clear`). Prioridade: base importada → base embutida `src/data/pocos-ba.json` (`BDOE_POCOS_FILE` nos testes) → vazia. O campo Poço/Locação (`autocomplete: 'pocos'`) sugere poços (exato → sem zeros à esquerda → contém) e, ao escolher, preenche as coordenadas (`source: 'base'`); coordenadas de GPS/digitadas só são trocadas com confirmação. Arquivo inválido nunca substitui a base atual. Importação com mais da metade dos pontos fora da BA/SE é recusada (lat/lng trocadas ou UTM). A base embutida atual é a real da UO-BA (6.421 poços, gerada de `pocos_UO-BA_verificacao.csv`; o KML equivalente bate 100%). Ao sair do campo Poço com nome exato, só preenche coordenadas se o foco não foi para Latitude/Longitude e elas estiverem vazias. Testes usam bases fictícias em `tests/fixtures/`.
- **Contrato = lista dos contratos da conta** (`core/contratos.js` + `ui/contrato-campo.js`, tipo de campo `contrato` nos três relatórios e "Contrato padrão" nas Configurações): `my_contracts()` é baixado ao entrar / abrir / voltar a internet / "Sincronizar agora" e, nas verificações periódicas, no máximo a cada 5 min (`atualizarContratos`, chamado no `syncNow` antes do pull; o pull usa a lista guardada). Guardado POR USUÁRIO em `localStorage` `bdoe.contratos` (funciona offline); usuário local ou outro e-mail → lista vazia. Comparação igual ao servidor (`normContrato` = `_norm_contrato`: maiúsculas e separadores não importam — qualquer sequência que não seja letra/número vira UM espaço, pontas aparadas; "Os Mans" = "OS-MANS" = "os.mans", mas "OSMANS" é outro) — variação de escrita vira o nome da lista. Padrão: único contrato ou `contrato_padrao` se estiver na lista. Valor antigo fora da lista vira opção extra "(não vinculado à sua conta)" e é mantido. Sem contratos: select desabilitado + aviso "Nenhum contrato vinculado à sua conta…", sem asterisco, e o `required` do BDO é ignorado. Lista mudou → `FormView.atualizarContratos()` e Configurações redesenham. Testes: `tests/contratos.spec.js`; `vincularContratos(page, lista)` em helpers.js para testes que escolhem contrato.
- **Histórico da equipe (pull, `core/pull.js`)**: com login no Supabase e internet, baixa para o `history` local os relatórios dos últimos 30 dias (`PULL_DIAS`) dos contratos do técnico, com as fotos (`report-photos`), via RPC `list_team_reports` / `my_contracts`. Quem é de qual contrato é definido SÓ no servidor (tabela `contract_members`: e-mail + contrato, mantida pelo administrador; e-mail precisa estar confirmado; contratos comparados sem maiúsculas/espaços). Dispara ao abrir o app, no login e no evento `online` (`syncNow({ pull: true })`), senão no máximo a cada 15 min (`SYNC.pullIntervalMs`); "Sincronizar agora" também. Registros recebidos: `remote: true`, `autor`, `baixadoPor`, `fotosPendentes` (refeitas na próxima vez); status "Da equipe", só consulta/PDF/Reutilizar; nunca sobrescrevem relatórios do aparelho. Entrar com OUTRO usuário apaga os recebidos por quem saiu (`limparEquipeDeOutroUsuario`). Como ficam no `history`, entram na consolidação 14x14, no "Antes x Depois" e no BDO-e ativo da herança. Relatório sem contrato não é compartilhado. Testes: `tests/supabase.spec.js`.
- **Histórico local** (IndexedDB `history`, DB v2): todo relatório finalizado é copiado **com as fotos** ao entrar na Caixa de Saída e **fica no aparelho mesmo após o envio** (`sentAt` gravado em `confirmDelivered`); "Editar" remove e o reenvio regrava. Na atualização v1→v2 o conteúdo da fila é copiado (teste em `tests/atualizacao-banco.spec.js`). Registros antigos sem fotos guardadas avisam na prévia.
- **Aba Histórico** (id `outbox`, `src/ui/outbox-view.js` + `outbox.reports()`): lista histórico ∪ fila com tipo, poço, data do relatório e status (Aguardando envio / Reagendado / Enviado), filtro por tipo. Tocar abre a prévia `mode: 'view'` com "Gerar PDF / Imprimir" e "Reutilizar / Editar como novo" (novo rascunho com NOVO uniqueId; não copia data/hora, fotos, assinatura nem consolidação). A prévia tem barra `.modal__nav` no topo: "Voltar e editar" e "Início / Novo relatório" (`onNewReport`, apaga o rascunho com confirmação). Testes: `tests/historico.spec.js`.
- **Consolidação 14x14** (Relatório de Execução): campo `type: 'consolidation'` + `src/core/consolidar.js`. Com Poço/Locação + início/fim da quinzena (padrão: últimos 14 dias), agrupa automaticamente os BDOs do poço no período (atividades e horas, paradas, SMS/RPT) e o último status de equipamentos da Visita Técnica do poço. O resultado é congelado no relatório ao finalizar; é refeito ao abrir a aba e pelo botão "Atualizar consolidação". No PDF fica fora da grade de campos (`.preview__consol`) para paginar bem; partes vazias não aparecem.
- Códigos de válvula (VA-1, VB-2…) não contam como poço no resumo (`CODIGO_VALVULA` em `resumo-bdo.js`).
- O **BDO-e** tem **Coordenadas GPS** (`coordenadas()`, tipo `geo`) no bloco de identificação, **somente leitura** (Visita/Execução herdam): vêm só do botão "Obter Localização Atual" ou do poço escolhido na base (não há digitação; "Limpar" apaga). **Não saem** na prévia, no PDF nem no Word (nem links de rota).
- **Cabeçalho dos relatórios** (`src/ui/cabecalho.js`, prévia/PDF/Word): só Poço/Locação, Cidade/Campo (`campo`|`cidade_uf`), Data (`data`|`data_hora`), Turno, Cliente, Contrato e Equipe (`equipeTexto`, sem nomes repetidos), no quadro `[data-ident]`; esses campos (`CAMPOS_CABECALHO`) não se repetem nas seções.
- **Word (.docx)** (`src/ui/docx-doc.js`, `buildDocxBlob`): OpenXML gerado no aparelho sem bibliotecas (ZIP "store" próprio): cabeçalho de página com logo/empresa/título, rodapé "Página X de Y", quadro de identificação, seções só com dados, fotos em tabela de 2 colunas (48% cada, gridCol 4626), Antes x Depois lado a lado e a imagem da assinatura. Botão "Baixar Word (.docx)" na prévia: desktop via IPC `docx:save`; navegador pelo painel "Word pronto" (`showPdfSheet({ kind: 'Word' })`). Mesmas regras de conteúdo do PDF — ao mudar um, mude o outro (`pdf-doc.js`, `report-pdf.js`). Testes: `tests/docx.spec.js`.

Na apropriação, `chain`: a linha nova começa na hora fim da anterior.

Testes: `tests/resumo-bdo.spec.js`.

Nada de `window.open` (o Safari bloqueia). No desktop continua o `printToPDF` do Electron. O link do WhatsApp também usa o PDF.
- **Câmera** (`ui/camera.js`): tela cheia, barra fixa na base (Fechar · Tirar Foto · Alternar câmera, `z-index: 99999`), pinch-zoom bloqueado, zoom da câmera (+/−/barra) quando `getCapabilities().zoom` existe; "Tirar Foto" só libera com imagem no vídeo.

- **Deslocamentos com destino** (`core/deslocamento.js`): na atividade do BDO (ao sair do campo), "deslocando / indo / seguindo para", "iniciando deslocamento", "mobilizando"… + destino. Poço da base → Poço / Locação (+ coordenadas); cidade (`CIDADES`) ou base do usuário (Configurações › Bases e locais personalizados: "Nome; lat; lng") → Cidade / Estado. Soma o trecho (linha reta × 1,3) desde a última posição ao KM rodado; `row._desloc` evita somar duas vezes ao editar; pergunta "Deslocamento identificado para X. Deseja abrir a rota no GPS?".
- **Visual**: tokens com cantos 16px, fonte do sistema, contraste alto; no celular os modais são "bottom sheet" e os botões têm ≥ 48px.
- **Fotos** são comprimidas ao entrar (`ui/compress.js`: máx. 1280 px, JPEG 80%).
- **GPS**: selo "Localização capturada" no lugar das caixas de latitude/longitude (`[data-part]` continuam como `sr-only`).
- **Visita Técnica e Execução** seguem a sequência cronológica do modelo Word oficial: cabeçalho (com parágrafo de abertura gerado por `paragrafoAbertura()`) → chegada ao poço (placa e árvore de natal) → pressões e manômetros → um bloco por componente (Antipoço, VC, VA-1, VA-2, VB-1, VB-2, flange superior, flange inferior — listas `ANTEPOCO`/`VALVULAS_CABECA`/`FLANGES` em `modules/common.js`) → outras fotos → recomendações e assinatura (desenhada no quadro ou "Carregar imagem" PNG/JPEG, `loadSignatureImage`).

Fotos antigas sem `field` vão para "Outras fotos" (`assignPhotoFields`). No PDF ficam logo abaixo do componente como "Figura N — legenda", numeradas na ordem do relatório.
- **Antes x Depois** (Execução, campos `compare: true`): ao consolidar, `FormView.importBefore()` copia as fotos da última Visita Técnica do poço (histórico) para a coluna "Antes" de cada componente (`data._visita_ref/_visita_data`); só refaz se a Visita de referência mudar.

- Relatórios novos recebem padrões das **Configurações** (`settingsKey` nos campos). Empresa/logo são congelados em `data._empresa` ao finalizar.

## Regras de dados (não quebrar)

1. **Outbox**: todo relatório finalizado é gravado no IndexedDB **antes** de qualquer rede (`core/outbox.js`). Rascunhos também ficam no IndexedDB (fotos são Blobs).
2. **Trava de confirmação**: item só sai da fila com HTTP 200/201 **e** `id` devolvido para o `unique_id` (`core/sync.js`).
3. **Idempotência**: `uniqueId` (UUID) nasce com o rascunho e é a chave única no banco; reenviar nunca duplica.
4. **Escrita só por RPC** `security definer` (`submit_reports` → `bdo_reports` / `technical_visits` / `execution_reports` pelo `module`; `save_company_settings` → `company_settings`; `save_device_settings` é só compatibilidade). RLS ligado e sem políticas nas tabelas (a tabela única `reports` e `device_settings` ficaram como legado, copiadas pelo schema). `submit_reports` só para usuário logado (anon recusado) e só grava relatório SEM contrato ou de um contrato do próprio usuário (`my_contracts`); de outro contrato não é gravado nem confirmado (fica na fila do aparelho). Storage: bucket privado `report-photos` (fotos): INSERT só para logado, SELECT só para técnico logado do mesmo contrato (`can_read_report`); RPCs de leitura (`list_team_reports`, `my_contracts`) só para `authenticated`; bucket público `report-share` só para as cópias PDF e Word (.docx) do relatório (caminho = uniqueId).
5. Backoff: 3 tentativas imediatas, depois 30s → 15min com jitter. Fotos já enviadas não são reenviadas.
6. Mudou o esquema? Atualize `supabase/schema.sql` de forma idempotente (`if not exists`, `create or replace`). Mudança nova vai em `supabase/migrations/NNN_*.sql` (o que se roda no SQL Editor) e o MESMO texto no fim do `schema.sql`. Os testes rodam o schema num Postgres local (PGlite, `tests/banco.spec.js`, simulação do Supabase em `tests/sql/supabase-stub.sql`): dá para testar SQL sem tocar no banco real.
7. **Equipe e papéis** (migração `001_equipe.sql`): **não há "master geral" no app** — o Master (dono da licença) administra pelo Painel de Licenças e, no banco do app, só pelo SQL Editor (primeiro gestor de cada cliente, cota, gestores); no app quem manda na equipe é o **gestor do contrato**. `contracts` (`nome`, `nome_norm` = `_norm_contrato`, `max_technicians` default 2 = cota de técnicos ATIVOS; gestores não contam), `contract_members` com `id`, `contrato_id`, `user_id`, `nome`, `matricula`, `role` (`gestor`|`tecnico`), `ativo` (trigger `_contract_members_consistencia`: e-mail minúsculo, cria/liga o contrato, uma matrícula por pessoa — comparada sem pontuação/espaços por `_norm_matricula`, gravada como digitada). Leitura do papel: `my_access()` (`{ contratos: [{ id, nome, role: gestor|tecnico }] }`, só os do usuário). Gestão (só o gestor ativo do contrato): `team_list`, `team_add_technician` (trava o contrato e confere a cota; `p_somente_validar` para a Edge Function checar antes de criar a conta), `team_set_active` (só técnicos; gestores só por SQL). Mensagem de cota: "Entre em contato com o Master para ampliar a licença." Desativado sai do `my_contracts`. Login por matrícula (migração `002_login_matricula.sql`): `login_matricula(p_matricula, p_senha)` (anon) confere a senha NO BANCO (bcrypt do Auth via `extensions.crypt`) e só devolve o e-mail com a senha certa; o app então faz `signInWithPassword` do próprio IP (o limite do Auth é por IP — por isso não é Edge Function); 5 falhas em 15 min bloqueiam; matrícula inexistente gasta o mesmo tempo. **Edge Function `create-technician`** (`supabase/functions/create-technician/index.ts`, publicada pelo painel do Supabase, "Verify JWT" desligado): token do gestor → `team_add_technician` com `p_somente_validar` → `auth.admin.createUser` (e-mail confirmado, `user_metadata.must_change_password`) ou só vínculo se o e-mail já tem conta → `team_add_technician` de verdade; se falhar, apaga a conta criada. 400/401/403 (`codigo: sem_permissao|cota`)/409. JavaScript puro num .ts: testada em Node contra o banco local (`tests/edge-functions.spec.js`, helpers em `tests/sql/pg.js`). Histórico sem limite: `search_team_reports(p_query, p_module, p_before, p_limit)` (todo o acervo dos contratos do usuário, sem acento, 50 por página, máx. 200).

## Convenções de código

- JavaScript ES modules puro (sem TS, sem framework). Interface em português; código e nomes de campos em português sem acento (`poco`, `km_inicial`).
- **Formulários são dados**: para incluir/alterar campos edite `src/modules/*.js`; não escreva HTML de formulário à mão. Tipos e propriedades documentados no topo de `src/modules/common.js` (`span`, `divider`, `table` com `presetRows`/`computed`/`aux`, `geo`, `photos`, `signature`, `highlight`, `settingsKey`).
- Sempre escapar texto dinâmico com `esc()` (`src/ui/dom.js`). Sem `style=""` inline (CSP); use classes ou `el.style` via JS.
- Ícones: `icon(nome)` de `src/ui/icons.js` (SVG). Não usar emoji na interface.
- Nunca usar `alert/confirm/prompt` nativos: use `confirmDialog()` (`src/ui/confirm.js`) e `toast(msg, 'success'|'error'|'info'|'warn')`.
- Status na interface: "Pendente de Envio" (fila `outbox` do IndexedDB = sync_queue; reagendado = "Pendente de Envio (reagendado)"), "Sincronizado" (confirmado pelo servidor), "Salvo no aparelho" (só local). O evento `online` dispara o envio (`startSyncScheduler`).
- Editar item da Caixa de Saída só se `canEdit(rec)` (nunca houve tentativa de envio); `rehydrate()` reconstrói tabelas com linhas fixas.
- Em scripts de edição com `String.replace`, cuidado: `$$` na string de substituição vira `$` (use `split/join`).
- Testes E2E em `tests/` (Playwright + Electron real). Rode `npm test` antes de concluir mudanças de interface. Use `openTab(page, id)` (espera `#view[data-ready=id]`) em vez de clicar na aba direto.
- Cores e espaçamentos via tokens CSS em `src/styles.css` (`--primary`, `--surface`…), com tema claro/escuro.
- Datas exibidas em pt-BR; datas de arquivo usam data local (nunca `toISOString()` para "hoje").
